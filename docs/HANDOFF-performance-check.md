## Method
Test **production** (`https://vencyatelier.com`), because Cloudflare's caching, compression and HTTP/2 or HTTP/3 are part of the result. Use the local server only to A/B suspects.

### Step 1 — Lighthouse (lab, mobile + desktop)
```bash
npx lighthouse https://vencyatelier.com/ --preset=perf --form-factor=mobile --screenEmulation.mobile --throttling-method=simulate --output=json --output=html --output-path=./perf/lh-home-mobile --chrome-flags="--headless=new"
npx lighthouse https://vencyatelier.com/ --preset=desktop --output=json --output=html --output-path=./perf/lh-home-desktop --chrome-flags="--headless=new"
```
- Run every page × {mobile, desktop} × **3 runs**, and report the median (Lighthouse varies between runs).
- From the JSON, capture: Performance score, LCP, FCP, TBT, CLS, Speed Index, the **LCP element**, total bytes, and the top 5 opportunities and diagnostics (`uses-optimized-images`, `modern-image-formats`, `offscreen-images`, `uses-long-cache-ttl`, `render-blocking-resources`, `unused-javascript`, `total-byte-weight`).
- Put the output in `C:\Users\Jose\projects\vency-testing\perf\` (the testing repo), **not** in this repo.

### Step 2 — Fix the Playwright harness (`vency-testing/perf/perf-report.js`)
This is the one allowed code change, because it's in the testing repo, not the site.
- LCP: `new PerformanceObserver(l => …).observe({type:'largest-contentful-paint', buffered:true})`, read after load plus ~1 s. Record the element tag and src too.
- CLS: use the same observer pattern with `layout-shift`, `buffered:true`, and ignore entries where `hadRecentInput`.
- Add a mobile profile: `devices['Pixel 7']` plus CDP `Network.emulateNetworkConditions` (Slow 4G: 150 ms RTT, 1.6 Mbps down) and `Emulation.setCPUThrottlingRate({rate:4})`.
- Use 5 runs and a true median.
- Break bytes down by type: image, video (**new**, because `media` resources are currently uncounted or lumped in), JS, CSS, font, document and fetch.
- Keep the existing budgets, and add `videoKB` (mobile ≤ 1500 is a suggested starting budget; flag it, don't fail on it).

### Step 3 — Real-user data (field)
- PageSpeed Insights / CrUX for the origin: https://pagespeed.web.dev/analysis?url=https://vencyatelier.com. The site may not have enough traffic for CrUX; if not, write "insufficient data".
- Cloudflare dashboard → Web Analytics / Speed for the zone, if it's enabled. Note what's available. **Ask the human for access; don't guess.**

### Step 4 — Targeted checks (DevTools or script)
1. **Hero:** in the Network panel, check when the video starts downloading relative to the poster, whether `preload="auto"` competes with CSS and fonts, and whether LCP is the poster image.
2. **Below-the-fold video on mobile:** is `hero-clip-3to5.mp4` fetched before the user scrolls? How many bytes?
3. **Images:** list every image above 200 KB that each page actually downloads (from network logs, not from grep), with its rendered size against its intrinsic size.
4. **Caching:** `curl -sI https://vencyatelier.com/styles/styles.css?v=75` and the same for one image, one mp4 and one woff2. Record `cache-control`, `cf-cache-status`, `content-encoding`, and whether it's served over h2 or h3.
5. **API:** check the TTFB of `/api/availability` and `/api/catalog-archive`, and whether the page waits on them before showing content.
6. **Main thread:** take a Performance trace on mid-tier mobile (4× CPU) for `/` and `/catalogo.html`. Note long tasks over 50 ms and which script causes them.
